# Shrimply Study (repo: StudyQuizWebApp)

React study app (flashcards, multiple choice, typing) hosted on GitHub Pages. The user's libraries live in their Google Drive, saved automatically as they work (asked for), or, signed out, in this browser; a `.shrimp` file is only a copy they open or download. A library shared with a link is view only for everyone but its owner.

## Workflow
- Build one step at a time, then stop. Don't start the next feature unasked.
- FEATURES.md is the ranked backlog. Update it at the end of every step.
- When the user asks for the "next step": suggest 1 to 3 `todo` items from FEATURES.md with a one-line reason each, then wait for their choice.
- Done means checked at the edges, not only with what happens to be on screen (asked for, after a long theme name wrapped in the sidebar's footer): every text a change shows that can vary (theme names, file, course, quiz and card names, counts, Drive file names, messages) is tried at its longest real value and at its shortest, in every place it shows, at the narrowest width that place can take (the 280px sidebar, the drawer below 800px, a pane under 480px, a 320px window), and in every theme (display fonts draw at different widths). One-line rows and controls never wrap, spill out or clip without an ellipsis (the whole text then in a tooltip or the open list); measure it (an element's height and its `scrollWidth` against `clientWidth`), never judge by eye. A new control or row that holds varying text gets an e2e check that walks those values (as `e2e/sidebar_tree.py` does for every theme name), so the bug can not come back.

## Commands
- `npm run dev`, `npm run build`, `npm run preview`
- `npm test` (vitest), `npm run typecheck`
- `python -I e2e/run.py`: the end-to-end tests (Python Playwright on a frozen build; see `e2e/README.md`)
- Deploy: push to `main` and `.github/workflows/deploy.yml` publishes to https://mrflamesjr.github.io/shrimply-study/ (repo `MrFlamesJr/shrimply-study`, Pages source: GitHub Actions, already set). A release that raises `FORMAT_VERSION` first adds that version's fixtures to `src/storage/fixtures/` (a file's `library.json` with every field, and a backup). A release with something new for users adds its notes at the top of `RELEASES` (`src/releaseNotes.ts`), dated the day it goes out, which shows everyone the welcome page once more with them.

## Architecture rules
- Storage only goes through `src/storage/`. Screens and state never touch files, zip, IndexedDB or localStorage directly (reading an image the user picks into a data URL, in `ImageSlot`, is input, not storage). Files go through the `StorageAdapter` alone: `useWorkspace` calls nothing else for them (open a copy, download a copy), so a new backend is a new `StorageAdapter`, swapped in at the single `useWorkspace(fileStorage, ...)` line in `App.tsx`. `src/state` imports no components (`Notify` lives in `logic/pushToast`, `Choice` in `model.ts`). Google Drive sits beside the file adapter, not instead of it: `googleDrive.ts` is the only file that talks to Google, `useWorkspace` reaches it (`lib.drive`, per open file), and the browser backup keeps which Drive file each library came from (`drive`). No library is saved to a local file: a library is a Google Drive file (autosaved, `where: 'drive'`) or a browser library (`where: 'browser'`, the IndexedDB backup) until it is uploaded; a `.shrimp` file is opened as a copy (a browser library) and downloaded as a copy, and closing never removes a library (it stays in the Explorer's closed files). There is one Google sign-in per browser (`shrimply-google-sign-in` in localStorage, shared by every tab, asked for); Sign out forgets the account and closes every Drive library everywhere. Browser preferences are one localStorage key each, named `shrimply-...` (so `resetPrefs` finds them), not part of the library: the chosen theme (`themePref.ts`), the study options (`studyPref.ts`) the last release whose welcome page was shown (`welcomePref.ts`) and whether the Explorer's right-click tip was seen (`explorerTipPref.ts`).
- File format: versioned; every older version keeps opening (asked for). `FORMAT_VERSION` (`model.ts`) is the current one; `format.ts` reads and writes only it, no fallbacks. Any change to what a file or the browser backup holds (a field or card type added, renamed, removed or read differently) goes in the next version: changes not yet on `main` share one version; the first one after a release raises `FORMAT_VERSION` and adds a step in `src/storage/upgrade.ts` that turns the previous version's data (file and backup form) into it (as is when something was only added). Old versions are handled there and nowhere else. A released version's step and its fixtures (`src/storage/fixtures/v<N>.json`, `v<N>-backup.json`) are never edited; `upgrade.test.ts` opens them all. A library from a newer version asks to reload. `library.json` has no ids and nests a quiz's grouped cards under `groups`; they are added in memory on open. Change `format.ts` in place.
- Every color, font, weight, text size, radius, line width, opacity, glow and spacing value is a token (see Themes). No hex/rgb values and no literal mix percentages outside the token files (component geometry like icon and control sizes, and media-query breakpoints, stay literal; a theme's images, its `.svg` files and `unicorn.webp`, bake in their colors, as tokens can not reach an image).
- Pure logic lives in `src/logic/` with a test file next to it.
- `src/kit/` is a reusable kit (asked for): generic parts any app could use (editor groups and splits, tabs, tree, context menus, selection, undo history, drag and drop, popup windows, shortcuts, confetti). It imports only React and itself (`kit/boundary.test.ts`), knows nothing of study data, and styles itself only with `--kit-*` variables, which `tokens.css` maps to this app's tokens. Contracts in `docs/architecture/`, one page per module in `docs/kit/`. `#/_workbench` (not linked) is a demo host that uses only the kit.

## Minimal code
- Ask before adding any dependency. `@dnd-kit` (asked for) sorts within one list: a sequence's steps (`StepList`) and the editor's cards (`EditorCard`, whose grip is `useSortableCard`). Moving things between places (tabs, the Explorer) is native HTML5 drag and drop (`kit/dnd`), which works across the app's windows.
- The kit is an exception to "no abstraction until something is needed twice" (asked for).
- Smallest code that works. No abstraction until something is needed twice. Plain CSS; no UI kit, router or state library. Props, not context.
- Keep the file map below accurate when adding files.

## Themes
- Every style edit is for all seven themes, not just the one on screen: think through how it reads with each theme's colors, display font, corners, glow and backdrop. It is not done until the theme check (the last item of this section) passes.
- Files, the same for every theme: `src/theme/tokens.css` holds what all themes share (derived colors and theme-independent tokens). Each theme, Calm included, is one file `src/theme/theme-<id>.css` imported in `main.tsx` after `tokens.css`, plus an entry in `THEMES` (`model.ts`, the first is the default). Calm's block is `:root, :root[data-theme="calm"]`, so a missing or unknown `data-theme` gets it; every other is `:root[data-theme="<id>"]`. A theme file holds tokens only. Never style elements in it and never edit component CSS for one theme: a missing hook becomes a new token that is a no-op in Calm (like `--glow-*`).
- One template: every theme file is an about-comment (the look and each color's job), then one block with `color-scheme: dark` and exactly the tokens of `theme-calm.css`, in the same order, under the same section comments; only the values differ (`themes.test.ts` checks it). Sections: ground and text (`--bg`, `--text`, `--muted-l`, `--muted-c`), color jobs (`--ok-fill`, `--bad-fill` and `--role-ink`: the right and wrong buttons filled solid where `--role-solid` is 1, as in Kahoot; `--accent`, `--accent-fill` and `--accent-ink` (the filled accent buttons and their text: the accent itself, or a deeper step of its hue where the accent is too light to carry text, as in Quizlet), `--selection-color`, `--ok`, `--bad`, `--danger`, `--warn`, `--info`, `--explain`, `--ink`), the shrimp (`--brand-shell`, `--brand-head`), blanks (`--blank-1` to `-4`), the eight `--group-*`, elevation (`--lift-*`; `--lift-sidebar` is the sidebar's own step, the first surface's unless set apart; `--lift-side-block` and `--lift-side-active` the sidebar tree's file blocks above it, the active file's), the filled accent buttons (`--hover-*`, and `--accent-hint`: how much of their text a key hint on them keeps), tints (`--tint-*`, `--tint-side-active` among them: how much accent the active file's block takes, `--tint-keep` too: how much of the ground's own color stays under a role's tint, `--role-chroma` and `--role-turn`: how colorful a right or wrong fill is and how far its hue turns away from yellow, `--role-solid`: right and wrong buttons filled solid, `--group-fill` / `-line` / `-chip`, scrim alphas), glow (`--glow-*`), backdrop (`--backdrop`, `--backdrop-drift`, `--backdrop-drift-w`, `--backdrop-drift-time`), type and shape (`--font-display`, `--display-*`, `--title-size`, `--text-brand`, `--text-score`, `--text-info-title`, `--text-side-title`, `--text-result`, `--radius`, `--radius-pill` (the add-card pills: round, or the theme's `--radius` where corners are sharp)), the explanation banner's edge (`--explain-edge`, `-w`, `-h`, and `-fill`: the same tile's line and everything right of it, where the banner's fill shows, so none of it shows left of a shaped line, asked for). A value may use another template token (`var(--accent)`), never a token of the theme's own. Themes never override derived colors: a look the formulas can not give becomes a new knob, added to every theme file at once (Calm's value keeps Calm unchanged).
- Derive, don't repeat: surfaces and borders are relative oklch from `--bg`, lighter by a `--lift-*` step, gaining `--lift-chroma` color per step, in the hue `--lift-hue` (Calm: 0, a warm rose brown the user chose). Tints are `color-mix` with a `--tint-*` strength; hover is relative oklch from the accent. Never use a near-grey's own `h` in relative oklch: browsers drop it as powerless (it becomes 0), so the hue is a token.
- One job per color, so a screen never shows more than a couple of strong colors: the accent is the one action, the selection and the focus ring (a ring of another hue beside the accent clashes); green and red only mean right and wrong; `--warn` (yellow or orange in every theme) only a warning, or a correct option left unpicked in a pick-all question (Missed, asked for); `--danger` only means deleting for good; `--info` only info; `--explain` only a card's explanation (the feedback sheet's banner). Group colors are a touch softer than the accent so they never compete with it.
- Colors over colors agree in temperature and hue: main text is a near-neutral white; muted text takes the surfaces' hue (`--muted-l`, `--muted-c`, `--lift-hue`); a tinted zone (danger zone, group box, a right or wrong answer and its outline button) sets `--zone` and is listed in the zone rule at the top of `base.css`, which leans its muted text and borders toward that color by `--tint-muted`; bright text never sits straight on a colored surface (`--tint-rest` gives the outline buttons a faint fill of their own color). Judge a tint by its real composite (its OKLCH hue against the role's, in every theme and over every ground it sits on), never as a lone swatch.
- Color theory, applied for real and reasoned in OKLCH (perceptual, so equal steps look equal; never in hex or HSL, whose lightness is wrong): lightness (L) does hierarchy and contrast, hue (h) does meaning, chroma (C) does emphasis.
  - Value first: a screen must read in greyscale (ground, surfaces, text and the one action told apart by L alone) before hue helps.
  - Harmony: each theme is built on a named scheme of its ground and accent hues (Calm is complementary: gold accent at h 83 opposite the cool ground at h 258, warm rose-brown surfaces between). A new hue is placed by its angle to those: analogous (within about 30°), complementary (about 180°), split-complementary (about ±150°) or triadic (about 120°). When a theme's colors are chosen or changed, its about-comment names the scheme.
  - Proportion: about 60% ground and surfaces, 30% structure (muted text, lines, tints), 10% or less strong color; the accent is the smallest, brightest area.
  - Chroma by area: the bigger the area, the lower its chroma (surfaces near grey, tints faint); high chroma only on small marks. On a dark ground, saturated color glares and looks brighter than its L (Helmholtz-Kohlrausch), so lower C before L.
  - Temperature: warm and bright come forward (the action), cool and dark recede (ground, structure).
  - Peers (the `--group-*` colors, the blanks) share one L and C and are spread around the hue wheel, so each weighs the same and neighbors never look alike.
  - No vibrating pairs: two high-chroma colors at about the same L (complements, red beside blue) never touch; part them by L or drop one's C.
  - Simultaneous contrast: a color shifts with what surrounds it, so judge it on every surface it sits on, never as a lone swatch.
  - Color blindness: about 1 in 12 men can not tell red from green by hue, so color is never the only sign of meaning (right and wrong also show a mark or a word).
- Choosing a color: take the token whose job it is; never invent a color for one spot. When no token fits, the new token gets a value in every theme file at once, placed by that theme's scheme (above), not Calm's value copied. Two saturated colors never sit straight against each other (a solid badge on another color's fill, one color's text on another's): one steps back to a tint or a muted line.
